# Phase 10 Task 2 — Cloud AI Integration

## What was implemented

This task completed the existing cloud AI adapter integration without changing the offline-first local rule engine or the ActionProposal confirmation flow.

- Added a real, configurable cloud AI adapter boundary in `src/features/ai/adapters.ts`.
- Kept the local Khata AI engine as the primary path for deterministic financial actions and queries.
- Made the cloud provider optional and resilient: disabled, misconfigured, timed-out, HTTP-failing, or malformed responses gracefully fall back to the local AI.
- Ensured the cloud layer only receives a safe summary of business totals and public-facing metrics, never raw financial tables.
- Preserved the existing `ActionProposal` → confirmation → executor workflow for all write actions.

## Architecture and data flow

1. User enters an AI prompt on the AI page.
2. `askAI()` in `src/features/ai/adapters.ts` calls the local engine first.
3. If the local engine can answer or create an action proposal, that result is returned.
4. If the local engine returns a fallback, the app checks `CloudAIAdapter.isAvailable()`.
5. The cloud adapter sends only a safe summary payload generated by `summarizeData()`.
6. If the cloud request fails, times out, is invalid, or returns malformed data, the app falls back to the local AI flow and honest user-facing messaging.
7. No cloud response is ever trusted to create or modify a financial record directly.

## Environment variables / configuration

Use Vite environment variables only for non-secret frontend configuration:

```bash
VITE_AI_ENABLED=false
VITE_AI_PROVIDER=openai-compatible
VITE_AI_ENDPOINT=https://example.com/api/ai
VITE_AI_MODEL=gpt-4o-mini
VITE_AI_TIMEOUT_MS=8000
```

- `VITE_AI_ENABLED`: enable/disable the cloud path.
- `VITE_AI_PROVIDER`: provider label for the backend wrapper.
- `VITE_AI_ENDPOINT`: URL to a secure backend/proxy endpoint.
- `VITE_AI_MODEL`: non-secret model name used by the backend.
- `VITE_AI_TIMEOUT_MS`: request timeout in milliseconds.

No API key or provider secret is stored in the frontend bundle or in `src/`.

## Secure deployment requirements

The cloud AI endpoint must be implemented on a trusted backend or secure proxy that owns the provider credentials. The frontend must never store or transmit any secret key. The backend should:

- keep API keys in server-side environment variables only,
- validate request payloads,
- perform the actual LLM call,
- reject or sanitize unsupported queries,
- never expose raw backend errors to the browser,
- treat the LLM as advisory-only and read-only for conversational responses.

## Fallback behavior

The application continues to function when:

- the user is offline,
- the cloud provider is disabled,
- the endpoint is unreachable,
- the response is invalid or malformed,
- the request times out.

The fallback path remains the existing local AI engine and local response templates.

## Safety guarantees

- Financial writes are never executed directly from an LLM response.
- All write actions still go through the deterministic `ActionProposal` → user confirmation → executor flow.
- The cloud adapter only sends aggregated, safe summary numbers and metadata.
- Full customer tables, payment tables, sales tables, and raw database records are never sent to the cloud provider.
- Cloud AI is treated as a conversational helper only, not as a source of truth for financial mutation.
